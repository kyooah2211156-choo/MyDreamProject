# 강아지 유치원 운영 관리 서비스 계획

## 확정된 결정
| 항목 | 결정 |
|---|---|
| 형태 | 웹(반응형). Swift 앱은 웹이 안정된 뒤 같은 서버를 공유해 추가 |
| 기술 | Next.js + Supabase (DB, 로그인, 사진 저장, RLS) |
| 유치원 정지 | 읽기 전용(조회만 가능, 작성·변경 불가) |
| 유치원 해지 | 접근 차단 |
| DB 연결 | 개발용 Supabase 프로젝트 사용. 운영용은 배포 직전에 별도 생성 |

## 용어
- **테넌트**: 가입한 유치원 하나. 유치원끼리 데이터가 섞이지 않게 분리한다.
- **RLS**: DB가 "이 사용자는 이 행만 볼 수 있음"을 직접 강제하는 기능.
- **MCP**: AI 프로그램이 외부 도구나 데이터에 연결하는 표준 방식.

## 사용자와 권한
| 역할 | 할 수 있는 일 |
|---|---|
| 서비스 운영자 | 가입 승인/반려, 유치원 이용 상태 관리. 유치원 내부 알림장은 못 봄 |
| 원장 | 자기 유치원 전체 관리, 직원 초대·권한·퇴사 처리 |
| 선생님 | 부여된 권한 범위의 강아지, 출결, 알림장, 공지 |
| 보호자 | 연결된 자기 강아지의 발행된 알림장, 출결, 공지만 조회 |

## 첫 버전 기능
1. 유치원 가입 신청과 운영자 승인
2. 원장의 직원 초대와 권한 관리
3. 강아지 등록과 보호자 연결
4. 날짜별 등원 예정, 등원·하원 관리
5. 알림장(식사, 배변, 활동, 특이사항, 사진), 임시저장과 발행
6. 유치원별 공지
7. 운영자의 유치원 이용 상태 관리

**후속 단계:** 자동 결제, 이용권 차감, 차량 위치 추적, CCTV 연동.

## 핵심 규칙
- 모든 유치원 소속 데이터에 `kindergarten_id`를 붙이고 RLS로 강제한다.
- 보호자는 연결된 강아지의 "발행된" 정보만 본다. 임시저장은 못 본다.
- 직원이 퇴사(`left`) 처리되면 다음 요청부터 접근이 막힌다.
- 사진은 비공개 저장소에 두고, 권한 확인 후 일정 시간만 유효한 주소로 보여 준다.
- 폰은 하단 탭, PC는 좌측 메뉴.

## MCP 설계 (용도 분리)
**용도 1. 개발 도우미(Kiro):** 개발용 DB와 개발 도구에만, 가능하면 읽기 전용으로 연결한다. 운영 DB에는 연결하지 않는다.

**용도 2. 서비스 안의 외부 AI:** 로그인한 사용자의 권한으로만 동작한다. 전용 만능 계정을 만들지 않는다.
| 도구 | 종류 |
|---|---|
| 출결 조회, 알림장 조회 | 읽기 |
| 알림장 초안 작성 | 쓰기(초안만) |
| 알림장 발행 요청, 출결 변경 요청 | 확인 필요 |

확인 필요 작업은 `pending_actions`에 대기 요청으로 저장한다. 사용자가 화면에서 대상과 내용을 보고 확인해야 실행되고, 요청은 일정 시간 후 만료된다. 모든 AI 호출은 `audit_logs`에 남긴다.

## 화면
- **공통:** 로그인, 회원가입, 초대 수락, 내 정보
- **운영자(PC):** 가입 신청 목록/상세, 유치원 목록과 상태 변경
- **원장/선생님:** 오늘 대시보드, 출결, 알림장(목록·작성·미리보기·발행), 강아지, 공지, 직원 관리(원장), AI 요청 확인함
- **보호자(폰):** 내 강아지 선택, 오늘의 알림장, 지난 알림장, 출결 기록, 공지

## 개발 순서와 완료 조건
| 단계 | 내용 | 완료 조건 | 진행 |
|---|---|---|---|
| 0. 준비 | 프로젝트, DB 연결 | 빈 화면이 폰과 PC에서 열리고 DB에 접속됨 | 완료 |
| 1. 로그인과 유치원 분리 | 로그인, 역할 구조, RLS 기본 틀 | 유치원 A 직원이 B 데이터를 조회하면 0건(자동 테스트 통과) | 완료 |
| 2. 가입/승인/이용 상태 | 가입 신청, 승인·반려, 상태 변경 | 승인 시 원장 계정 생성, 정지 시 원장이 데이터 조작 불가 | 완료 |
| 3. 직원 관리 | 초대, 수락, 권한, 퇴사 처리 | 퇴사 처리 직후 해당 직원의 모든 조회와 수정이 거부됨 | 구현 완료, 실제 화면 확인 대기 |
| 4. 강아지/보호자 | 강아지 등록, 보호자 연결 | 보호자는 연결된 강아지만 보이고, 연결 해제 즉시 안 보임 | 예정 |
| 5. 출결 | 등원 예정, 등원·하원 | 날짜별 목록이 맞고, 하원은 등원 후에만 가능하며 변경 기록이 남음 | 예정 |
| 6. 알림장 | 작성, 임시저장, 사진, 발행 | 임시저장은 보호자에게 안 보이고 발행하면 보임, 사진 주소가 권한 없이 안 열림 | 예정 |
| 7. 공지 | 작성과 조회 | 다른 유치원 보호자에게 안 보임 | 예정 |
| 8. 외부 AI(MCP) | 조회/초안 도구, 확인 대기 흐름, 감사 로그 | AI의 발행·출결 변경 요청은 대기 상태로만 남고 사용자 확인 후에만 반영, 권한 밖 조회 거부 | 예정 |
| 9. 마무리 | 반응형 점검, 권한 전체 테스트, 배포 | 역할 4종 × 주요 화면 점검표 통과, 실제 폰 확인 | 예정 |

## 서비스 시작 전 확인할 것
- Supabase **Confirm email**(이메일 인증)을 다시 켠다. 꺼 두면 남의 이메일로 가입해 초대를 가로챌 수 있다.
- 초대 링크는 지금 이메일로 자동 발송하지 않고, 원장이 링크를 복사해 직접 전달한다(미확정 10번).

## 보안 운영 원칙
- `service_role`, `sb_secret_` 키, DB 비밀번호는 채팅과 코드에 넣지 않는다.
- 접속 키는 `web/.env.local`에만 두고 git에 올리지 않는다.
- 개발용 데이터에는 가짜 정보만 쓴다.
